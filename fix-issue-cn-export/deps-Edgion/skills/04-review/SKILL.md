## Usage principles

> **Index discipline** — entries below are a quick decision index. Older entries
> may contain more rationale than the preferred shape; do not expand that pattern.
> When adding an entry:
> - Add only after the conclusion is verified against the current code and design semantics.
> - Keep it to a single line. The reusable judgment criteria, rejected fixes, source paths,
>   and regression-test names live in the linked per-finding file (the canonical home);
>   add a concise `CLOSED-FINDINGS.md` row.
> - If design goals change, update the per-finding file first (the canonical home), then
>   this pointer if its trigger or verdict changed.

- When reviewing plugin findings of the form "response/request body filter cannot modify body content / `UpstreamResponseBodyFilter` only gets a read-only `&Option<Bytes>` and returns only `Option<Duration>` / plugins can't drop/replace body bytes like Envoy's `encodeData`/`decodeData` / no request-body access for plugins / HMAC `validate_request_body` returns 'body not supported' (filter-01, filter-05)": **accepted tradeoff (filter-01, 2026-05-29)**. Read [architecture/body-filter-read-only-by-design.md](architecture/body-filter-read-only-by-design.md). The body-filter phase is intentionally bandwidth-throttle-only; the read-only contract is chosen at `PluginRuntime::run_upstream_response_body_plugins`, the only shipping consumer is `BandwidthLimit`, and no plugin needs body mutation today. The "make the trait `&mut` + `BodyFilterResult`" and "add a `RequestBodyFilter` trait" fixes are not accepted as narrow review fixes — body mutation is a wide-impact plugin-SDK feature that belongs in `tasks/todo/` via brainstorming. Verify the absence of a shipping body-mutation consumer before re-reporting.

- When reviewing request-body mutation findings of the form "the first upstream attempt fixes `Content-Length`/`Transfer-Encoding`, but a retry clones the original downstream framing after the plugin body view is released" (BODY-001): **fixed (BODY-001, 2026-07-27)** — [architecture/request-body-retry-framing-metadata.md](architecture/request-body-retry-framing-metadata.md). Final modified-body length is immutable attempt-lifetime metadata; every attempt reapplies it while unmodified request framing remains untouched. Retaining the plugin-readable view or sharing a plugin/upstream cursor is not accepted.

- When reviewing request-body mutation findings of the form "capture obeys the gateway physical body cap, but ExtProc or ProxyRewrite can publish an arbitrarily larger body" (BODY-002): **fixed (BODY-002, 2026-07-27)** — [architecture/request-body-mutation-physical-cap.md](architecture/request-body-mutation-physical-cap.md). The immutable cap lives in `BodyStorageView`; overwrite and slice replacement validate checked final length before atomic publication. Per-plugin duplicate checks and caller-supplied mutation caps are not accepted.

- When reviewing request-body policy findings of the form "`EdgionGatewayConfig.spec.requestBody` is frozen in `EdgionHttpProxy` at listener construction / EGC updates require a restart or Gateway requeue" (BF-01): **fixed (BF-01, 2026-07-28)** — [architecture/request-body-policy-egc-hot-reload.md](architecture/request-body-policy-egc-hot-reload.md). EGC resources and pre-resolved body policies share one immutable `ArcSwap` snapshot; each new request performs one bounded lookup and copy. Listener rebind, Controller Gateway requeue, per-request parsing, and expanding the fix into multi-GatewayClass support are not accepted.

- When reviewing over-limit request-body findings of the form "`capture_request_body` drains the remaining client body before returning 413 / a slow chunk sender can hold the request task indefinitely" (BF-02): **fixed (BF-02, 2026-07-28)** — [architecture/request-body-over-limit-immediate-reject.md](architecture/request-body-over-limit-immediate-reject.md). Physical-cap violations return immediately without drain; HTTP/1.x disables connection reuse, while HTTP/2 ends and resets only the rejected stream. Per-read timeout, a configurable drain deadline, pre-response shutdown, and closing the shared HTTP/2 connection are not accepted.

- When reviewing generic request-body gate findings of the form "`RequestBodyBuffer` must materialize a disk spill merely to enforce its body limit / every gated plugin can safely defer full reads to its own error policy" (BF-03): **fixed (BF-03, 2026-07-28)** — [architecture/request-body-gate-lazy-materialization.md](architecture/request-body-gate-lazy-materialization.md). Filters require materialization by default to preserve the body gate's failure policy; `RequestBodyBuffer` explicitly opts into capture-and-length-only behavior. This does not make DSL `req.body` streaming.

- When reviewing ExtProc findings of the form "the response count matches, but duplicate/reordered headers responses satisfy an exchange without the required body verdict" (BODY-003): **fixed (BODY-003, 2026-07-27)** — [architecture/ext-proc-phase-verdict-matching.md](architecture/ext-proc-phase-verdict-matching.md). Every verdict is matched to the ordered outstanding phase before any mutation is applied; missing/wrong verdicts use `failureModeAllow`, and `ImmediateResponse` is terminal.

- When reviewing ExtProc findings of the form "headers and the original body are sent together, so `CONTINUE_AND_REPLACE` is ignored or times out" (BODY-004): **fixed (BODY-004, 2026-07-27)** — [architecture/ext-proc-interactive-continue-and-replace.md](architecture/ext-proc-interactive-continue-and-replace.md). Phases are sent interactively on one bidi stream, terminal verdicts stop later phases, and the final request message half-closes immediately. Response-header body replacement remains explicitly unsupported and follows `failureModeAllow`.

- When reviewing request-body digest findings of the form "a bodyless request has no `BodyStorageView`, so its valid SHA-256 empty digest is rejected as incomplete" (BODY-007): **fixed (BODY-007, 2026-07-27)** — [architecture/request-body-empty-digest.md](architecture/request-body-empty-digest.md). Bodyless admission hashes its canonical empty result directly; declared bodies still require complete bounded capture. Synthetic downstream reads and treating arbitrary missing views as empty are not accepted.

- When reviewing request-body injection findings of the form "ExtProc can receive an empty body phase but cannot replace a truly bodyless request with non-empty bytes" (BODY-008): **fixed (BODY-008, 2026-07-27)** — [architecture/bodyless-request-replay-owner.md](architecture/bodyless-request-replay-owner.md). Mutations lazily install an application-finalized empty V0 through Pingora's dedicated bodyless replay seam; capture and ready-replay registration remain separate, and the fork stays pinned by immutable rev.

- When reviewing RequestMirror findings of the form "an earlier request plugin commits a body mutation, but the detached mirror receives no body or must share the upstream replay cursor" (BODY-014): **fixed (BODY-014, 2026-07-27)** — [architecture/request-mirror-committed-body-snapshot.md](architecture/request-mirror-committed-body-snapshot.md). A mirror clones the current immutable committed bytes without touching Pingora replay; the no-view path remains streaming, each hop owns framing, and discarded mirror responses are never aggregated.

- When reviewing controller findings of the form "status write failures are silently dropped / `persist_k8s_status` failure only logs a `tracing::warn!` with no re-queue / no eventual consistency / `observedGeneration` left stale / `kubectl wait --for=condition` may hang / should re-queue on reconcile error like controller-runtime (controller-01)": **accepted tradeoff (controller-01, 2026-05-29)**. Read [handler-requeue/status-write-no-retry-accepted.md](handler-requeue/status-write-no-retry-accepted.md). Non-404 write failures decompose into two self-healing classes — configuration/setup errors (admission webhook reject, 422 schema, 403 RBAC) heal when the operator fixes the spec → `MODIFIED` → reprocess; reference errors heal via the six cross-resource requeue paths. `requeue_with_backoff` was deliberately removed (`skills/01-architecture/01-controller/04-workqueue.md`) because this layer cannot distinguish transient from permanent failures, so a blind "re-queue on non-404" would loop forever on permanent errors (403/422/409). The residual purely-transient case (429/503 + healthy watch + no follow-up event) is rare and self-heals on the next relevant event. The "`enqueue_after` on non-404", "reintroduce exponential backoff", and "add a status-write-failure condition" fixes are not accepted. Verify against `persist_k8s_status` in `resource_controller.rs` before re-reporting.

- When reviewing `TimeRangeCondition::evaluate` silent `parse_from_rfc3339` swallow / malformed `timeRange.after`/`before` ignored / time-gate permanently inert / no preparse signal / bypasses `seal_fail_closed` (plugins-runtime-F002): **fixed (plugins-runtime-F002)** — [plugin-metadata/conditions-timerange-preparse-validation.md](plugin-metadata/conditions-timerange-preparse-validation.md). Generalised rule: operator-echoed header-name insert failures funnel through PluginLog, not `tracing`.

- When reviewing findings of the form "listener port set is frozen at startup / `partial_update` never re-binds sockets / adding a port to a live Gateway is silently dropped / no Envoy-LDS-style runtime listener add/remove without restart (listener-01)": **documented limitation (listener-01, 2026-05-30)**. Read [architecture/listener-port-set-frozen-at-startup.md](architecture/listener-port-set-frozen-at-startup.md). Sockets bind once in startup Phase 1 (`configure_listeners`); the Pingora `Server` is then consumed by `run_forever()` (`cli/pingora.rs`), so `partial_update` (`runtime/handler.rs`) has no handle to bind/drain sockets and rebuilds routing data only — TLS certs hot-reload via ArcSwap, port changes need a process restart. The real fix is blocked on Pingora exposing post-`run_forever()` `Service` registration; the "make `partial_update` call `add_service()`" and "emit a warn/status condition for unbound ports" fixes are not accepted as narrow review fixes (the latter is a separate `tasks/todo/` feature). The limitation is now documented in `01-startup-shutdown.md` + a code comment, and the misleading "dynamic listener/TLS config updated" log was corrected. Verify the new doc/comment before re-reporting.

- When reviewing findings of the form "Gateway keeps config in memory only / cold restart blackholes traffic until full resync / no last-good disk snapshot / no Envoy warm-start / Controller restart forces full relist (sync-05)": **accepted tradeoff (sync-05, 2026-05-31)**. Read [architecture/gateway-no-local-config-snapshot.md](architecture/gateway-no-local-config-snapshot.md). Edgion already has the property that matters — a running Gateway whose Controller dies keeps serving last-good in-memory config; the real gap is only the Gateway **process cold start** (`wait_for_ready` blocks Pingora until the first full List per kind). That gap is **not** below the Envoy/Istio default baseline: stock Envoy loses in-memory xDS on process restart too, `--restart-epoch` hot restart is a same-host live-process handoff (not disk persistence, useless for pod/node recreate), and disk warm-load only exists via filesystem-xDS deployment tricks. Single-pod restart is covered by readiness probe + multi-replica + PDB; only correlated Controller+all-Gateway restart is exposed (rare). The "persist to disk + warm-load + tentatively-ready staleness flag + incremental Watch via server_id/sync_version" direction is a large cross-layer feature (medium risk: serving stale config, cross-kind consistency), not a narrow review fix — promote to `tasks/todo/` via brainstorming if ever prioritized. Verify the architecture entry before re-reporting.
